# Product data runtime source contract

This is source implementation, not deployment or acceptance evidence. Tests, dependency installation, image builds, SQL application, CI and runtime integration have not been executed in this change. Every optional service is off by default. The supplied environment examples contain deliberate `REQUIRED_...` placeholders and cannot enable a service as supplied.

## Artifacts

`ArtifactService` reserves owner/idempotency-key metadata in PostgreSQL before GCS writes. Browser upload/download access uses a five-minute HMAC token bound to authenticated owner, artifact UUID and operation; its path is the application API, never a raw GCS object URL. The API must enforce its normal owner authentication in addition to this token. Maximum artifact length is 16 MiB; length and SHA-256 are checked before upload and on generation-pinned readback. GCS writes use `ifGenerationMatch=0`; an uncertain upload is reconciled by its reserved object key and verified bytes. No automatic object replacement, artifact deletion, PostgreSQL hot-data deletion or retention purge is implemented.

Enable only with `ARTIFACT_STORAGE_ENABLED=true`, an existing own `ARTIFACT_GCS_BUCKET`, and either `ARTIFACT_SIGNING_SECRET` or `OMNIAGENT_BUNDLE.artifact_signing_key` of at least 32 bytes. Secret values belong in pinned Secret Manager versions, never in the example environment files. `ArtifactService.metadata` is an internal database row and must not be serialized to a browser because it includes the internal object key.

Production factories also require `ARTIFACT_LIMITS_JSON={maxOwnerBytes,maxGlobalBytes,maxOwnerObjects,maxGlobalObjects}` with explicit positive safe-integer ceilings and owner ceilings no greater than global ceilings. No budget values are supplied implicitly. Reservation serializes under a PostgreSQL transaction advisory lock, checks existing owner/idempotency keys before charging, and sums every reserved object and byte across **all states**, including uploading, uncertain and rejected. A missing cloud object or rejected upload does not release capacity automatically. Quota rejection precedes the metadata INSERT and any GCS upload. The optional constructor argument without budgets exists only for older isolated fixtures; production factories must always supply parsed limits.

## Jobs, schedules and private worker

`services/job-worker/Dockerfile` builds the worker without Flutter. Runtime enablement requires all of:

- `AGENT_JOBS_ENABLED=true`, a canonical HTTPS Cloud Run `AGENT_JOBS_AUDIENCE`, and explicit service-account emails in `AGENT_JOBS_ALLOWED_EMAILS`.
- Explicit UUIDs in `AGENT_JOBS_APPROVED_OWNER_IDS`; schedule and claim SQL only visits these owners.
- The existing own database URL from `OMNIAGENT_BUNDLE.chat_database_url` or `CHAT_DATABASE_URL`, `CHAT_DATABASE_TLS_MODE=verified-ca`, a PEM/base64 trust anchor and the verified PostgreSQL hostname settings used by Chat API.
- At least one configured workflow, archive or analytics handler. Other handlers stay unavailable.
- Explicit `JOB_QUEUE_LIMITS_JSON={maxOwnerPending,maxGlobalPending,maxOwnerSchedules,maxGlobalSchedules}` positive safe-integer ceilings, with each owner ceiling no greater than its global ceiling. Missing or malformed budgets reject enablement.

`POST /internal/jobs/tick` requires Google service identity with the configured audience and approved email. Its only optional input is `{"maxJobs":1}` (integer 1–3). One concurrent tick per instance is allowed. It atomically advances at most 25 due schedules, then executes bounded claims; no scheduler is created automatically. An existing approved scheduler may invoke the same endpoint. `scripts/omniagent-data-lifecycle-tick.sh` provides an explicit manual invocation with an impersonated approved service account.

Jobs have owner-scoped idempotency keys, 60-second leases, 20-second heartbeats, fenced completion, cancellation and a 120-second execution deadline. Lease loss cannot overwrite a later worker's result. At most three abandoned lease claims are recovered; further recovery requires human reconciliation. Configured handlers are read-only workflows, export-idempotent archive writes and BigQuery queries with reserved remote job IDs. Cancellation aborts cooperatively and cannot undo an already accepted remote request. Failed/uncertain remote writes must be reconciled using their original identifier.

New job enqueue, schedule creation and scheduler-generated enqueue share a transaction advisory lock and the same capacity checks. Pending capacity counts queued/running jobs; schedule storage counts all schedule records including disabled schedules. Matching idempotent replays do not consume capacity twice. A due schedule at pending capacity stays due without enqueue or advancing its clock, allowing the tick to continue draining existing jobs. Terminal job history is retained; the pending ceiling does not claim to be a retention or total-history storage budget.

Completion/failure/cancellation notifications are durable owner-scoped in-app outbox entries. Workflow success with `changed=false` stays quiet. No email is sent. `GET /internal/jobs/metrics` uses the same private identity checks and returns state counts/durations, configured analytics ceiling and explicit `actualCost:null`; it never claims a ceiling is actual spend.

Migration `013_data_lifecycle_jobs.sql` creates the own tables and NOLOGIN group roles. Operators must explicitly grant `omniagent_jobs_app` to the reviewed Chat/worker login and `omniagent_iceberg_writer` to a separate writer login. Neither group gets DELETE. The writer needs only its export ledger, not general Chat data. Runtime credentials must select those scoped login roles. SQL table/index creation is retryable; a migration journal remains the canonical applied-version record.

`infra/gcp/deploy-product-worker.sh agent|jobs|archive [--apply]` requires explicitly provided `OMNIAGENT_GCP_PROJECT`, `OMNIAGENT_GCP_REGION` and `PRODUCT_WORKER_*` service, identity, immutable image, environment file, pinned Secret bindings, network/subnet and candidate tag. It defaults to plan-only; `--apply` requests an authenticated zero-traffic candidate with one instance/concurrent request. It does not build images, grant IAM, apply migrations, promote traffic or invent resource names. Existing Cloud Run invoker IAM and database/catalog/GCS permissions are separate requirements.

## Actual MCP workflows

`AGENT_JOBS_WORKFLOWS_JSON` maps an application workflow key to `{template,sources}`. Supported templates and required source slots are:

| Template | Sources | Local result |
| --- | --- | --- |
| `github-drive-progress` | `github`, `drive` | Canonical progress record additions, updates and removals |
| `weekly-life-plan` | `calendar`, `life` | Due-ordered Life task proposals in unoccupied 30-minute Calendar windows over seven days; explicit UTC 09:00–18:00 planning hours |
| `janus-life-risk` | `janus`, `life` | Janus risk signals with missing values explicit and Life items to review |
| `taiwan-activity-shadow` | `taiwanActivity` | Shadow-only candidate time/location/duplicate validation; zero external writes |
| `gmail-life-inbox` | `gmail`, `life` | Optional read-scope inbox triage and Life planning evidence; zero sends |

Each source has the exact existing `serverId`, fully qualified `toolName`, bounded `arguments`, `readOnly:true`, and an optional operator-supplied projection. No tool names, source IDs, resource names or domain contracts are invented. `AGENT_JOBS_MCP_POLICY_JSON` is the existing ChatMcp owner→server→`{configRef,tools}` policy. Calls go through the authenticated own gateway with its existing owner-signing bundle key and the exact approved `CHAT_GATEWAY_URL`/`CHAT_GATEWAY_AUDIENCE`. External OAuth is supplied through these existing approved MCP grants, including Gmail read scope if enabled. Configuration labels do not grant capabilities: operators must bind only actual read-only grants/tool contracts; no generic write tool belongs in a workflow source.

A projection is `{rootPath?,parseJson?,itemsPath,fields}`. Paths are explicit dot-separated property/index paths (no expression evaluation); `parseJson:true` decodes a bounded JSON string at `rootPath`, useful for actual MCP text responses. `itemsPath` must resolve to at most 100 records. `fields` maps normalized names to the actual provider paths. Allowed names are `id,title,summary,url,status,priority,start,end,due,updatedAt,risk,severity,location,unread`. Missing projected fields remain null. Missing projections return `configuration_required`; mismatching arrays/fields fail honestly. Actual tool output shapes must be established from the approved bounded integration before configuration. Projected records, rather than wrapper timestamps, determine meaningful changes. Suggestions remain local; Calendar or Life writes must use the existing Agent approval runtime with explicit owner approval.

Optional source `argumentBindings` maps exact existing top-level tool argument names to `ownerId`, `now`, `weekStart` or `weekEnd`. The worker resolves these from authenticated job context; times are ISO UTC and the week starts Monday 00:00 UTC. This supplies rolling Calendar/Drive time filters without a stale fixed date or accepting client-supplied owner IDs. Bindings do not invent argument names: use only fields actually documented by the approved existing tool.

## Real Iceberg archive writer

`services/archive-writer` is an own Python HTTP service that uses PyIceberg and Arrow to append a real Iceberg snapshot in an **existing configured** BigLake REST catalog/table. It never treats a JSON object in GCS as an Iceberg table. The unavoidable separate Python dependencies are pinned in its requirements: PyIceberg 0.12.0, Arrow 26.0.0, gcsfs 2026.10.1, google-auth 2.62.0 and psycopg 3.3.6. Package metadata and public APIs were read from [PyPI PyIceberg metadata](https://pypi.org/pypi/pyiceberg/json), [PyIceberg API](https://py.iceberg.apache.org/api/), [configuration](https://py.iceberg.apache.org/configuration/) and [snapshot API](https://py.iceberg.apache.org/reference/pyiceberg/table/snapshots/). No dependency installation, compatibility build or live catalog validation has occurred; transitive dependencies are not a generated lockfile.

Writer enablement requires `ICEBERG_WRITER_ENABLED=true`, its canonical Cloud Run `ICEBERG_WRITER_AUDIENCE`, and these operator-provided JSON objects:

- `ICEBERG_CATALOG_JSON`: `{approved:true,name,uri,project,warehouse}`. `uri` must be the official `https://biglake.googleapis.com/iceberg/v1/restcatalog`, `warehouse` must be an existing own `gs://` bucket and `project` the approved own project. ADC authenticates both the Google REST catalog and own GCS. No table/catalog/bucket creation occurs.
- `ICEBERG_OWNER_TABLES_JSON`: owner UUID→`{table,identifier,gcsPrefix}`. `identifier` is the exact existing `namespace.table`; the public contract `table` is `catalogName.namespace.table`; `gcsPrefix` is the exact approved own table prefix below the configured warehouse, ending in `/`.
- `ICEBERG_CALLER_GRANTS_JSON`: approved service-account email→array of owner UUIDs. A verified Google identity token must match both audience and owner grant.
- `OMNIAGENT_BUNDLE.chat_database_url` (or the own `CHAT_DATABASE_URL`) and mounted absolute `ICEBERG_DATABASE_SSLROOTCERT`. The Python writer forces libpq `sslmode=verify-full`, a five-second connection timeout and scoped statement/lock timeouts. At most two request-scoped database sessions exist per process; it has no unbounded connection pool. Its DSN hostname must match the actual certificate; no permissive fallback or IP hostname bypass exists.

The existing table must have exactly five required string columns, in this order: `owner_id`, `export_id`, `source_sha256`, `content_type`, `payload_json`. Bounded UTF-8 `text/plain`, `application/json` and JSON-suffix media types are accepted; unsupported/binary artifacts remain in verified hot storage. JSON media types must contain valid JSON. Each artifact becomes one owner/export-bound envelope row. `payload_json` stores canonical JSON with exactly `{contentType,text}`; `text` preserves the original decoded UTF-8 source, including whitespace, quotes and control characters. The original source SHA-256 is checked against the **decoded text encoded back to UTF-8**, never against the reserialized canonical envelope. Actual snapshot readback verifies both envelope content type and original source bytes/digest. Canonical envelope expansion is bounded to six times the 16 MiB source cap plus fixed metadata overhead. This is an envelope archive, not schema inference or a claim that arbitrary source JSON automatically becomes domain analytics columns.

`POST /v1/iceberg/exports` accepts the exact ArchiveWriter commit object (`operation,exportId,ownerId,sourceSha256,table,contentType,bytesBase64`) and matching `Idempotency-Key`. `GET /v1/iceberg/exports/:exportId?ownerId=...` independently loads the configured catalog, finds the exact owner/export snapshot summary, scans that snapshot with server-side owner/export filters and verifies its row/digest. A successful receipt contains `format:"iceberg"`, export/owner/source/table bindings, actual decimal `snapshotId`, `committed:true` and `recordCount:1`. Missing export is 404; uncertain/missing committed snapshot or conflicting identity is 409; unavailable catalog or unknown commit outcome is 503. Lookup is bounded to 1,000 retained snapshot metadata records, four scan files and 64 MiB, and verifies snapshot/data paths stay under the approved own prefix. Reconciliation exceeding those limits fails explicitly.

The PostgreSQL ledger and session advisory lock serialize requests for an export ID. `prepared` is committed before any write; `uncertain` is committed **before** calling Iceberg append. If append or its response is lost, subsequent lookup reconciles the actual snapshot. An uncertain export without a matching snapshot is never automatically appended again. An expired snapshot is never silently accepted from a cached receipt. No hot-data purge, Iceberg overwrite, snapshot expiration or garbage collection occurs.

Chat/worker archive config is `ARCHIVE_ENABLED=true` with `AGENT_JOBS_ARCHIVE_CONFIG_JSON={url,audience,table,approved:true}` pointing to that own deployed writer. Audience must equal its approved Cloud Run origin. The adapter verifies the submitted bytes and source digest, checks the commit response, then `ArchiveService` requires an independent GET receipt. Missing own catalog/table, schema, IAM, writer origin, CA or owner/caller grant is an explicit deployment blocker, never fabricated acceptance.

## BigQuery / BigLake analytics

`ANALYTICS_ENABLED=true` and `AGENT_JOBS_ANALYTICS_CONFIG_JSON={project,dataset,table,location,maximumBytesBilled,maxOwnerDailyQueries,maxGlobalDailyQueries,approved:true}` explicitly enable a configured existing BigQuery or BigLake external table. The table must expose `owner_id` and `event_time`. Resource identifiers are validated; no user SQL is accepted. The fixed query filters owner on the server, requires a lookback of at most 31 days, limits rows to 1–1,000, sets a ten-second job timeout and caps the approved per-query billing ceiling at 1 GiB. Explicit positive safe-integer owner/global daily query ceilings are required; owner must not exceed global. These are approved limits, not measured charges.

The application reserves an owner/idempotency-key→remote-job mapping before `jobs.insert`. Retries use the same BigQuery job ID. Readback checks both owner mapping and configured project/location; it never accepts an arbitrary client job ID. Query responses are bounded to 2 MB. Background analytics polls for at most one minute and leaves running/uncertain results explicitly requiring readback/reconciliation. No project, dataset, external table, BigLake connection, IAM role, budget approval or billing resource is created implicitly.

Before any Google request, a READ COMMITTED transaction and global advisory lock check the existing owner/idempotency key, then count reserved queries for the current UTC day across the owner and globally. Failed/uncertain reservations remain charged conservatively. An existing matching key retains its remote job ID without consuming a second reservation. Per-query bytes and daily query counts jointly bound repeated submissions; actual billing remains explicitly unavailable.
